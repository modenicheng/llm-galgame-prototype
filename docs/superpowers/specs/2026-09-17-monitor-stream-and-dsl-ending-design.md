# 后台监控连续流与 DSL 收尾容错设计

**日期：** 2026-09-17  
**状态：** 已确认，可直接实施

## 目标

在不放松 Gal DSL 主协议的前提下，提高模型段尾输出的成功率，并把编剧 LLM 监控从“逐请求切换查看”改为一份可持续阅读的实时文档。同时提升事件面板的信息层级，并在连续 DSL 文档中标出玩家当前正在阅读或操作的位置。

## 范围

本次包含四项相互关联的改造：

1. 优化 `@end` 相关提示词，减少模型遗漏 `/?`、漏写 `end` 或写错结束行的概率。
2. 对两类语义唯一的段尾错误做有限自动修复，同时继续拒绝不明确或疑似截断的输出。
3. 将编剧 LLM 输出呈现为一个自动滚动的连续文档，请求和重试作为文档边界嵌入其中，并展示每次请求的 token、耗时、行数、事件组和结束状态。
4. 重新设计已提交事件列表的视觉层级，并在 DSL 文档中高亮玩家当前位置。

不改变 DSL 的正式语法，不接受任意缺失的 `@end`，不自动猜测 nonce 或 reason，不把普通正文中的 `@` 当作结束标记。

## 方案选择

### 方案 A：删除 `@end`

由流结束或任务类型推断段落状态。实现表面简单，但无法可靠区分正常收束、网关截断和模型提前停笔，也会削弱 nonce 的串流隔离能力，因此不采用。

### 方案 B：只强化提示词

保留全部严格校验，仅重复强调结束格式。改动风险最低，但不能兜住已经观察到的 `@ <nonce> interaction` 和遗漏 `/?`，仍会触发整段修复请求，因此不采用。

### 方案 C：严格协议 + 有限修复

正式协议仍要求 `/?` 和 `@end <nonce> <reason>`。提示词在任务开头锁定结尾模板；运行时只修复语义唯一的结尾笔误。该方案保留截断检测和 nonce 校验，同时消除最常见、最明确的机械错误，因此采用。

## DSL 收尾协议

### 提示词结构

系统协议在“玩家交互表单”后立即给出固定收尾模板，并将收尾自检缩短为可执行的三步：

1. 表单以 `/?` 闭合。
2. 下一行原样输出 `@end <nonce> <reason>`。
3. `@end` 后不再输出字符。

每个任务模板在正文要求之前先声明本次允许的结尾。交互型任务直接展示两行固定尾部：

```text
/?
@end {nonce} interaction
```

非交互任务直接展示相应的 `buffer` 或 `ending` 行。这样把结束约束放在模型规划输出的位置，而不是只在长协议末尾警告。

### 有限自动修复

新增一个纯文本修复器，仅接受以下精确形态：

```text
@ <expected-nonce> <allowed-reason>
```

并规范化为：

```text
@end <expected-nonce> <allowed-reason>
```

约束如下：

- nonce 必须与当前请求完全一致。
- reason 必须在当前请求允许集合中。
- 整行除空白外不得有其他字符。
- 规范化后的 sentinel 仍由现有 `DslSegmentParser` 校验；若后面还有内容，继续报 `SENTINEL_NOT_LAST`。
- 不修复 `end ...`、`@ending ...`、错误 nonce、未知 reason 或只有 `@` 的残片。

当合法或已规范化的 `interaction` sentinel 到达，而一个内容完整的表单仍处于打开状态时，解析器自动补入 `form_end`，提交该交互后再提交 sentinel。该修复仅在表单本身能够通过 `InteractionBuilder.finish()` 时发生；空问题、空选项等仍按原错误拒绝。`buffer` 或 `ending` 遇到未闭合表单仍报错。

每次自动修复都会产生监控事件，显示修复类型、源行号和说明，避免“静默纠错”。

## 请求级观测数据

`DslStreamObserver` 增加两类只读信息：

- 请求用量：输入 token、输出 token、缓存输入 token、数据来源（API 或估算）、总耗时、首 token 延迟。
- 有限修复：`end_keyword` 或 `form_close`、源行号、说明。

这些数据进入 `MonitorHub` 的有界 writer task ring，并同时出现在快照和增量事件中。现有字符数、解析行数、事件组数、结束 reason、错误和重试状态继续保留。

## DSL 来源位置与当前行

每个由流式解析器提交的 `EventGroupDraft` 携带可选来源：

```ts
interface DslSourceLocation {
  attemptId: string;
  lineIndex: number;
}
```

普通台词、旁白和 beat 使用产生该组的主行号；交互组使用 `?` 起始行号，而不是 `/?` 或自动修复所在行。没有经过真实 LLM 流的测试桩和旧会话可以不带来源。

`Game` 在编译组时建立 `line_id / interaction_id → DslSourceLocation` 的会话内映射。向玩家发出 `playback_ready` 或 `interaction_opened` 前更新 `GameMonitorState.currentDsl`。这份映射只服务实时观测，不写入存档；恢复旧会话时允许当前位置为空。

监控前端按 `attemptId + lineIndex` 定位文档行。交互位置会高亮从 `?` 到 `/?` 的整个表单块。自动跟随开启时，当前行优先于文档末尾成为滚动目标；用户主动向上滚动后暂停自动滚动，回到底部后恢复。

## 连续 DSL 文档

### 信息架构

取消任务和尝试的切换 chips。所有保留在 writer ring 中的请求按时间从旧到新排列在同一个滚动容器内：

```text
┌ 请求边界：续写 · 18:42:03 · #0 · 生成完成 ─────────────┐
│ in 2,481  out 316  cached 2,048  1.8s  8 行  5 事件组 │
└───────────────────────────────────────────────────────┘
  1  林澈: ……
  2  ? 你要怎么接话？
  3  + ……
  4  /?
  5  @end 07b8 interaction

┌ 请求边界：分支预取 · 18:42:05 · #0 · 生成中 ─────────┐
│ out 83…                                              │
└───────────────────────────────────────────────────────┘
  1  ……
```

请求边界承担导航和统计，不再另设每段 footer。重试是同一任务下的独立请求边界；失败和修复记录显示在边界内，不把错误混入 DSL 正文。

### 视觉原则

监控页沿用现有深色运维界面和更纱黑体，不引入新依赖或装饰性动画。视觉重点只放在三处：当前玩家位置、错误/重试、结局/交互边界。

基础色板：

- `canvas #0c0c0f`：DSL 文档背景。
- `surface #121218`：请求边界和特殊事件底色。
- `muted #7d7d87`：常规元数据。
- `active #58a6ff`：玩家当前位置。
- `warning #d29922`：交互、修复和重试。
- `danger #f85149`：校验失败。
- `success #56d364`：正常结束和结局。

常规台词与旁白保持低对比、无卡片包裹；高频事件只用窄标记和轻量标签。请求边界、玩家操作、交互、结局、错误才使用有色背景或明显边框。当前行使用左侧蓝色轨道和低饱和蓝底，并提供“玩家当前在此”文本标记，不能只靠颜色表达。

## 事件面板

事件按频率和操作意义分三层：

- 高频普通：`dialogue`、`narration`。紧凑行高、弱化 kind，不使用彩色胶囊。
- 交互关键：`interaction`、`player_choice`、`player_input`、`player_dialogue`。使用蓝色或琥珀色左轨与清晰来源标签。
- 特殊终止：`end`。使用绿色强调面和结局标识。

事件文本保持为主体，seq 和类型退居辅助层。列表继续自动滚到底部，不为每行增加阴影或大圆角卡片。

## 错误处理与兼容性

- 旧快照缺少 token、repair 或 `currentDsl` 时，前端显示 `—` 或不渲染对应项。
- writer ring 仍限制 12 个任务、每次尝试文本仍受字符上限约束。
- 快照与增量事件必须产生相同的连续文档。
- 自动修复失败后继续走既有重试/失败路径，不能吞掉校验错误。
- 监控观察者异常不得影响生成主路径。

## 测试策略

1. 纯函数测试：只修复精确的 `@ <nonce> <reason>`；拒绝错误 nonce、reason、附加文本和普通 `@` 文本。
2. 解析器测试：完整开放表单 + `interaction` sentinel 自动补 `/?`；无效表单和其他 reason 不修复。
3. 生成器测试：修复事件、usage 和 DSL 来源行号通过 observer 发出；正常严格输出行为不变。
4. MonitorHub/模型测试：快照和增量都保留 token、修复记录和当前 DSL 位置。
5. DOM 测试：多请求同时展示、流式追加不清空旧请求、请求边界统计、自动滚动、玩家当前行/表单块高亮。
6. 事件面板测试：普通、交互、玩家操作和结局获得不同语义 class。
7. 全量门禁：`pnpm test`、`pnpm typecheck`、`pnpm build`。
