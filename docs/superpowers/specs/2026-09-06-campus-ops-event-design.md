# 校园技术社团值班事件分支设计规格

## 1. 设计目标

在现有 LLM GalGame 框架上，新增一个面向社团招新/展位体验的校园技术社团值班模式。它应当让玩家能够随时开始、自然进行若干轮互动、在合理时机结束；但本规格不把体验硬编码成固定轮数、固定时长、固定事件数量或固定结局协议。

这个需求属于一个独立产品分支，不应破坏 `main` 上正在发展的通用能力，尤其是长线剧情记忆、存档、叙事导演和未来可复用的引擎能力。特定活动内容、树莓娘人设适配、校园运维事件和展位 UI 优先留在功能分支；验证为通用能力的改动才回提到 `main`。

## 3. 主线与分支策略

### 3.1 `main` 保留内容

- 保留当前 LLM 生成、Gal DSL、分支预取、自由输入、音频、WebSocket、UI projection 等通用框架。
- 保留并继续发展长线剧情记忆、存档、narrative director、故事计划和未来可复用的通用结算/事件基础设施。
- 不在功能分支中删除或重写这些能力为一次性展位逻辑。

### 3.2 新功能分支内容

建议从当前干净的 `main` 创建独立分支，命名类似 `feat/campus-ops-raspberry`。分支只引入：

- 校园技术部值班语境；
- 树莓娘角色适配；
- 技术分享会、电脑诊所、镜像源维护、诊所预约后台、面试系统、工会/任务系统、校内云盘事件内容；
- 展位需要的开场、结局、重置和可见状态适配；
- 经验证确实通用的框架补丁，以独立提交形式保留，便于 cherry-pick 或合并回 `main`。

### 3.3 提交分层

建议将提交分成三类：

1. `chore/refactor`：框架通用改动，可回提 main；
2. `feat/campus`：本分支专属事件、人设、提示词与展位文案；
3. `feat/assets`：授权确认后的资源接入，未授权素材只能留在外部工作区，不能提交。

不要在同一个提交中混合通用引擎、校内具体内容和未经授权的美术资源。

## 4. 玩法语义

每局是一个独立的“校园技术部正在处理的事务”，但事件不必表现为固定的四轮问答。模型可以根据问题复杂度自然增加或减少交互：简单问题快速解决，权限冲突、同步故障、预约冲突、云盘恢复等问题允许多轮排查、沟通和复盘。

现有 `narrative.mode: event` 和 `max_interactions: 0` 已提供不限制互动的基础。新分支默认继续复用它，不把 `max_interactions` 改成剧情要求。若展位需要防止模型异常循环，可单独提供一个可选的保护阈值；它只在异常情况下触发，不得写入角色台词或作为玩家可见的固定轮数。

自由输入保持现有语义：它是玩家的一句话、问题或方案，不能直接声明“已经获得管理员权限”“文件已经恢复”等世界事实。系统根据当前事件状态决定采纳、拒绝、追问或部分采纳。

## 5. 内容范围

校园技术部可处理：

- 技术分享会：投影、音频、网络、讲稿版本、分享人迟到、现场提问、备用方案。
- 电脑诊所：电脑变慢、软件安装、校园网、输入法、打印机、显示器未通电、备份、隐私。
- 镜像源维护：同步延迟、版本不一致、存储不足、备用源切换、维护公告、影响范围。
- 诊所预约后台：重复预约、时间冲突、取消入口、志愿者排班、日期错误、备注滥用。
- 面试系统：错误通知、附件上传失败、时间错位、面试官缺席、题目版本、候选人隐私。
- 工会/任务管理系统：所有任务最高优先级、描述只有“救命”、重复任务、无人认领、跨社团协作、未关闭任务。
- 校内云盘：容量不足、共享权限、链接过期、同步冲突、误删恢复、文件版本、预览失败、活动资料截止。

以上是主题池，不是要求一次性实现完的硬性数量目标。应先做能验证玩法的最小事件集，再按现场测试反馈扩展。

## 6. 树莓娘适配原则

树莓娘应作为默认核心角色，但人设文案需要区分“已核对事实”和“本项目创作适配”：

- 已核对：网协看板娘、兔耳、粉色服装、参与技术分享和新成员面试、技术部语境。
- 本项目暂定表现：亲切可爱、认真值班、偶尔轻微傲娇；这些是本分支的角色演绎方案，不宣称为 BITNP 官方完整设定。
- 她不是全知管理员：可以接待、解释、记录、鼓励，也可以承认不确定并联系负责人。
- 她不能通过撒娇绕过权限、隐私、数据安全和服务变更边界。
- 旁观者要能一眼看懂她正在处理什么，不应把技术术语堆成门槛。

## 7. 资源策略

优先复用当前背景、DSL 和 StageRenderer。树莓娘立绘不使用当前苏遥/林澈素材替代；优先顺序为：

1. 获得 BITNP/资源作者明确授权后，按授权范围接入正式素材；
2. 若没有授权，使用本项目独立制作并确认不临摹/不混用的临时占位资源；
3. 组织 logo、活动 logo 和徽章图片也先核对可否用于本项目构建和现场展示，再决定是否打包。

不得直接从私有 `bitnp-raspberrygirl-vtuber-frontend` 复制分层部件或 Godot 资源到本仓库。素材引用要记录源仓库、commit、作者/许可、用途和是否允许再分发。

## 8. 非目标

- 不把项目变成真正的云盘、镜像源、预约后台、面试系统或工单系统。
- 不接入真实校园服务，不执行真实运维操作。
- 不要求一次性制作完整树莓娘 Live2D 系统。
- 不删除 main 的长线剧情记忆、存档或通用能力。
- 不把短局的展位建议（比如常见时长）上升为引擎硬限制。

## 9. 开放叙事修订（2026-09-07）

### 9.1 修订结论

本分支采用“**每局从可选叙事种子开始**”的方案，但叙事种子只负责提供一个开场起点，不是剧本、任务单或状态机。

本节优先级高于本文前文中任何可能被理解为“必须覆盖全部活动域”“每类事务都要有固定处理路线”或“结局必须落入某几类”的表述。前文列出的技术分享会、电脑诊所、镜像源、预约后台、面试系统、工单系统和云盘，统一降级为：

- 可供选择的叙事素材域；
- 事件种子来源；
- 内容统计标签；
- 后续扩展方向。

它们不是七条剧情轨道，也不是第一版必须实现的七个固定剧本。

### 9.2 叙事层次

校园技术社团是故事发生的场域，不是流程模板。内容分为三层：

#### A. 稳定世界规则

这部分可以长期写入角色和世界提示词：

- 故事发生在校园技术社团的值班、活动、协作或技术支持场景；
- 树莓娘可以接待、解释、排查、记录、提出建议，也可以承认自己不知道；
- 权限、隐私、数据安全、设备能力和负责人边界真实存在；
- 真实结果需要观察、验证、授权或明确的叙事事实支撑。

#### B. 本局叙事种子

每局只选择一个种子作为起点。种子可以来自预先登记的素材，也可以是后续新增的简短创作条目。种子只提供：

- 起始情境；
- 可见的初始问题或异常；
- 相关人物/物件/场所的少量线索；
- 可能值得留意的风险或矛盾；
- 可选的内容标签。

种子不得规定：

- 必须发生的事件顺序；
- 固定的互动次数或时长；
- 唯一正确路线；
- 必须出现的角色反应；
- 成功条件、失败条件或结局数量；
- 玩家必须采用的技术方案。

推荐的最小种子形态如下：

```yaml
id: old-device-before-opening
title: 开场前仍在运行的旧设备
seed: |
  技术分享会开始前，一台没人记得启动过的旧设备仍在运行。
  树莓娘只确认了它没有明显报错，但不知道是否应该现在关机。
tags:
  - 技术分享会
  - 旧设备
  - 交接不明
```

`title` 和 `tags` 主要用于选择、展示和统计；`seed` 是供模型理解起点的叙事素材，不是执行指令。

### 9.2.1 可选叙事种子样例

以下条目只是第一批可放入种子目录的素材方向。它们不对应固定剧本，也不规定会出现哪些人物、选择、技术结果或结局。实现时可以只接入其中一部分，也可以改写、合并或新增完全不同的种子。

| 种子标题 | 起始情境 | 可以自然牵出的矛盾 |
|---|---|---|
| 投影亮了，但没有画面 | 分享会开始前，投影仪通电但幕布无画面，备用设备在旁边。 | 先保证活动继续，还是继续排查；“已连接”是否等于可用。 |
| 电脑很慢，但不能直接重装 | 同学带来一台变慢的电脑，重要课程资料尚未备份。 | 排查效率、数据安全、重装风险和用户授权。 |
| 链接能打开，但文件不该公开 | 活动资料链接被转发，访问范围和文件敏感程度都不明确。 | 活动连续性、共享权限、访问记录和所有者确认。 |
| 镜像源看起来同步了，其实还没有 | 页面显示同步成功，但不同地点查到的版本不一致。 | 日志可信度、影响范围、备用源切换和维护公告。 |
| 打印机在线，但任务没有出来 | 预约打印任务停在队列里，暂时不知道是设备、账号还是队列问题。 | 先确认影响范围，还是直接清理队列；是否有备用打印点。 |
| 预约表里多出一个人 | 同一时间段出现两条预约记录，后台没有说明哪条是重复提交。 | 规则解释、人工确认、公平性和临时排班。 |
| 附件上传成功了吗 | 候选人说材料已上传，但面试官界面看不到附件。 | 上传成功与可见性的区别、隐私保护和备用提交方式。 |
| 所有工单都是最高优先级 | 任务列表充满“紧急”“救命”，但缺少影响范围和负责人信息。 | 如何补齐事实、排序、合并重复任务和协调跨组协作。 |
| 活动结束后仍在同步 | 活动资料已经使用完毕，后台却有一个不明同步任务持续运行。 | 是否停止任务、保留证据、确认所有者和处理资源占用。 |
| 交接文档写着“照旧处理” | 新值班成员接手时只拿到一句模糊备注，旧负责人暂时联系不上。 | 交接责任、谨慎行动、历史习惯和当前事实的差异。 |
| 一条旧链接指向了新文件 | 群里流传的链接仍然可用，但内容似乎已经换过版本。 | 版本确认、链接生命周期、信息一致性和误导风险。 |
| 树莓娘也不确定该不该关机 | 一台无人认领的设备正在运行，屏幕上没有明显错误，但用途未知。 | 保留现场证据、设备所有权、活动压力和最小风险操作。 |

这些种子可以跨越原先的活动标签。例如“旧链接指向了新文件”既可以发展为云盘问题，也可以转为版本管理、交接失误或社团协作故事。标签只帮助选种和统计，不限制生成方向。

#### C. 本局已确认事实

剧情推进过程中，只有已经进入 committed history 的内容才可以成为本局事实，包括：

- 玩家明确表达过的选择、判断和方案；
- 树莓娘或其他角色已经确认的信息；
- 已经执行且得到叙事内验证的操作；
- 被明确记录的未知项、风险和待确认事项；
- 本局人物关系、信任、误会或协作方式的变化。

结局只能依据这一层生成，不能回头把种子中的“可能”改写成已经发生的事实。

### 9.3 过程开放性

同一个叙事种子允许发展出不同类型的故事。它可以：

- 很快解决一个简单问题；
- 转为排查一个更深的技术原因；
- 变成权限、隐私或数据安全的讨论；
- 牵涉社团交接、责任确认或协作误会；
- 让树莓娘发现自己原先的判断不完整；
- 在玩家提出意外方案后改变关注点；
- 留下一个值得下一次值班继续追查的问题。

事件分类可以在过程中发生变化。例如“资料打不开”可以从云盘问题转为权限问题，再转为交接问题；运行时不需要强迫它始终属于一个 `category`。

每次玩家操作都应该产生与当前事实相符的反馈，但反馈不要求总是奖励玩家。合理反馈包括：

- 发现新线索；
- 暴露方案风险；
- 受到权限或资源限制；
- 证明原先假设不成立；
- 暂时维持活动，但留下后续隐患；
- 需要联系真正的负责人；
- 树莓娘认可、质疑、误解后修正，或暂时无法评价。

不得为了延长体验而强行添加无关事故，也不得为了快速结束而凭空补齐未验证的答案。

### 9.4 结局开放性

本分支不定义固定的结局枚举。以下内容只能作为可能的叙事形态，不能作为运行时协议或必达分类：

- 问题解决；
- 问题部分缓解；
- 方案暂缓；
- 转交负责人；
- 得到新的线索；
- 发现最初的问题描述有误；
- 技术问题落地，但人物关系发生变化；
- 事情暂时没有答案，留下后续调查方向；
- 玩家采取了有效但有代价的方案；
- 玩家没有解决问题，但避免了更大的风险。

技术上仍使用现有 `@end` 和 `EndEvent` 表示本局结束：

```ts
{
  type: "end",
  ending_id: "ending:<runtime-generated-id>",
  text: "依据本局已确认事实生成的自然结局"
}
```

`@end` 是引擎终止标记，不是内容层的结局模板。`ending_id` 不需要预先登记，也不应被解释为固定结局编号。

结局正文应当回应本局过程，但不强制套用固定字段或固定句式。它可以自然地写出：

- 发生了什么；
- 哪些内容被确认；
- 哪些内容仍然未知；
- 玩家和树莓娘接下来如何处理；
- 一个技术、协作或人物层面的余波。

如果故事已经自然落地，可以结束；如果当前仍有足够的叙事动力，也可以继续生成。不能仅因为某个内容标签已经出现，或因为达到预设轮数，就强行结束。

### 9.5 树莓娘的叙事角色不固定

树莓娘不再被限制为“说明问题 → 给选项 → 评价玩家 → 总结结果”的客服流程。根据本局种子和已确认事实，她可以承担不同功能：

- 值班接待者；
- 技术协作者；
- 现场主持或提醒者；
- 证据整理者；
- 对玩家方案提出质疑的人；
- 负责联系真正负责人的中间人；
- 掌握部分信息的当事人；
- 需要和玩家一起调查的协作者。

她可以犯有限且可被剧情纠正的判断错误，也可以表现出轻微的不耐烦、嘴硬、惊讶或认可；但她不能为了制造戏剧性而违反权限、隐私和事实边界。

### 9.6 选择与自由输入

玩家仍然可以使用 choice、input 或 hybrid：

- choice 提供当前已知情境下的不同策略，不承诺某个选项是唯一正确答案；
- input 接受玩家的问题、判断、表达或方案，不把文字直接当作已经执行的系统命令；
- hybrid 同时照顾快速体验玩家和愿意详细表达的玩家。

选项数量、交互模式和交互次数由当前叙事需要决定，不从种子中推导固定轮数。一个种子可以只产生一次交互，也可以在事实自然支持的情况下展开多轮。

### 9.7 第一版验收标准

第一版开放叙事验证不要求“七类活动域各完成一个剧本”，也不要求种子目录达到某个数量。应证明：

1. 每局能够从一条可选叙事种子开始；
2. 种子内容不会自动变成固定路线；
3. 同一种子允许不同的选择和自由输入；
4. 简单事件可以自然结束，复杂事件可以继续多轮；
5. 结局不依赖预设结局枚举；
6. 结局只依据本局 committed facts，不凭空补全结果；
7. 权限、隐私和数据安全边界仍然有效；
8. 下一局可以选择另一个种子，并与上一局的事实隔离。

### 9.8 对后续实现的约束

- 事件目录若实现，应称为 scenario seed/content catalog，而不是流程或任务状态机；
- 不新增 `success_path`、`failure_path`、`required_rounds`、`ending_count` 等字段；
- 不把七个活动域写成启动前必须存在的硬性集合；
- 不在 `Game` 中写入校园事务分支判断；
- 不新增固定结局、奖励或成就协议；
- 如果未来需要将种子传给 opening generator，应设计可复用的通用上下文接口，不能命名为校园专属接口；
- 任何可回流 `main` 的通用改动必须与校园内容、人设和资源提交分离。
